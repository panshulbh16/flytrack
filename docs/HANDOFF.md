# FlyTrack: handoff after Step 2 (backend)

Branch `backend`. Written 2026-11-22. Development continues in another session.

## 1. Decisions taken (user-approved)

| Topic | Decision |
|---|---|
| Maps | **MapLibre**: free, offline vector tiles possible (airplane mode) |
| Networking (Android) | **Ktor + supabase-kt** (no Retrofit; supabase-kt is built on Ktor) |
| Auth v0.1 | **Anonymous sign-in + Google**. Phone OTP in v0.2, because Indian SMS needs TRAI DLT registration |
| PNR | No PNR-only lookup: airlines have no public PNR API. The PNR is stored and parsed from the PDF or screenshot, and the flight is found by flight number + date |
| Ticket-parsing LLM | Opt-in, extracted text only. Primary **Claude Haiku 5.5** (`claude-haiku-5-5`); fallback Claude Sonnet 5.5. Set effort `low`, because thinking tokens are billed. No Chinese model was clearly better, and they add DPDP and reputational risk. Qwen3-VL on a US/EU host could be an A/B arm later |
| Instant alerts | Gate, belt, delay, cancel and boarding alerts are pushed in the same poll run that detects them. They go out as FCM **notification** messages on a high-priority channel, so Xiaomi/Vivo/Oppo/Realme battery killers can't block them. A separate data-only "sync" message updates the widget and live notification |
| UI | Match **HeyTurbulence (by Roamly)**. Tokens are in `docs/design-brief.md` |
| Min/target SDK | Proposed minSdk 26 and targetSdk 36, single Gradle module for v0.1. **Not yet explicitly confirmed** |

## 2. What Step 2 contains

* `supabase/migrations/20261122000001_init.sql` holds the tables:
  * `profiles`, `devices`, `airports`, `flights` (one row per unique leg), `user_flights`
  * `flight_status_history`, `flight_events` (unique `dedupe_key` = exactly-once alerts), `push_log`, `provider_calls` (the cost log)
  * Alert types: DELAY, DELAY_REDUCED, SCHEDULE_CHANGE, GATE_ASSIGNED, GATE_CHANGE, TERMINAL_CHANGE, BOARDING, DEPARTED, LANDED, BELT_ASSIGNED, BELT_CHANGE, CANCELLED, REINSTATED, DIVERTED, INBOUND_LATE (Pro)

  It also holds:
  * RLS and grants
  * trigger-maintained `tracker_count` / `pro_tracker_count`
  * a tracking limit (free 10, Pro 50)
  * `claim_due_flights()` (SKIP LOCKED lease), `register_device()`, `get_flight_recipients()`
  * `flight_view`, which masks Pro fields server-side
* `supabase/migrations/20261122000002_cron.sql` sets up pg_cron every 30 s, calling `invoke_poll_flights()`, which calls the Edge Function through pg_net. Secrets are in Vault. It also adds nightly housekeeping.
* Edge Functions:
  * `search-flight` (cache first, per-user rate limit)
  * `poll-flights` (cron only, `x-cron-secret`)
  * `provider-webhook` (`?token=` secret)
* `_shared/`:
  * the provider-agnostic `FlightDataProvider` interface, with `MockProvider` (clock-driven scenarios) and `AeroDataBoxProvider`
  * adaptive `schedule.ts`
  * `diff.ts`, which alerts against "what users were last told", plus the inbound-aircraft prediction
  * `notify.ts` (alert text in airport-local time)
  * `fcm.ts` (FCM HTTP v1 sender, RS256 JWT via WebCrypto)
* `seed.sql` has 7,917 airports with IANA time zones, generated by `scripts/import-airports.ts` from mwgg/Airports (MIT).

| Who tracks it | Provider calls per flight |
|---|---|
| Free users only | ≈107 |
| At least one Pro user (adds inbound-aircraft polling) | ≈175–200 |

Tunables are in `CADENCE` in `supabase/functions/_shared/schedule.ts`.

### Results from the simulator

* The gate change was pushed in the first poll after it happened (gate window: Pro every 2 min, free every 3 min).
* "Your plane is running late" (Pro) arrived about **130 min before** the airline's own delay notice.
* Free users never receive Pro alerts. Muted alert types are respected.
* A provider outage backs off and recovers without duplicate alerts. A webhook and a poll racing on the same change produce one push.

## 3. How to run every test suite

Deno unit and engine tests (no DB, no network after the first dependency download):

```bash
cd supabase/functions && deno test
```

Timeline simulator. The last digit picks the scenario: 0–2 on time, 3/4 delay, 5 gate change, 6 cancel, 7 inbound late, 8 belt change, 9 diverted.

```bash
cd supabase/functions && deno run tests/simulate.ts 2345 2347
```

SQL tests (RLS, triggers, lease, limits, exactly-once) on a throwaway local Postgres. The shim fakes `auth.*` and the Supabase roles.

```bash
scripts/test-sql.sh
```

If Postgres runs as the `postgres` OS user:

```bash
su postgres -c "cd $PWD && scripts/test-sql.sh"
```

Type-check all functions:

```bash
cd supabase/functions && deno check poll-flights/index.ts search-flight/index.ts provider-webhook/index.ts
```

Full local stack (needs Docker and the Supabase CLI):

```bash
supabase start && supabase db reset && supabase functions serve --env-file supabase/functions/.env
```

## 4. Review findings not fixed yet

An independent review ran 4 reviewers (alert correctness, SQL security, Supabase deploy, provider/FCM) and adversarially verified each finding: **29 confirmed, 0 rejected**. Some of them were duplicates of each other.

### Fixed in this branch (with regression tests)

* **Dedupe keys.** A value that came back (gate 12→15→12→15, delay 60→40→60, cancel/reinstate twice) was silently dropped. Keys now carry a generation counter (`alert_state.alertSeq`).
* **Stale snapshots.** An older snapshot (a late webhook, a registration lookup, a search) could overwrite newer data and alert falsely. `isStaleSnapshot()` now compares `providerUpdatedAt`.
* **Lost alerts on a crash.** Alert state used to be saved before the events. Events are now inserted first, and `sweepUnpushedEvents()` re-delivers anything inserted but never pushed (2–60 min old) at the start of every cycle.
* **FCM reliability.**
  * Concurrent sends now share one OAuth token, which is also cached per isolate.
  * Network errors, 429 and 5xx get 3 tries with backoff; a 401 re-mints the token. There is an 8 s timeout.
  * A missing `FCM_SERVICE_ACCOUNT_JSON` now **fails loudly** (`UnconfiguredPusher`) instead of quietly running in dry-run.
* **False cancel/reinstate pair.** `Canceled` ↔ `CanceledUncertain` wobble produced "back on" followed by another "cancelled". Reinstatement now needs a status that proves the flight operates.
* **Airline retimes.** A moved scheduled time sent no alert. There is a new **`SCHEDULE_CHANGE`** alert ("Rescheduled: 6E 2341 now 19:35"), with no follow-up "delay reduced".
* **Notification tags.** A terminal change shared a tag with gate alerts and could be replaced. It now has its own tag, and gate alerts show the terminal.
* **Diversion alert.** It used India time for a foreign diversion airport and could name the original destination as the new one. Both fixed.
* **Placeholder times.** "Took off --:--" and "Landed --:--" no longer appear; an unknown time is simply left out.
* **Tail swap.** After a swap, the old inbound link kept producing false INBOUND_LATE alerts. The flight is now unlinked immediately.
* **Through flights.** The inbound lookup skipped the real inbound leg on a through flight (same number, different leg). It now compares the departure airport too.
* **Endless polling.** Some end states never stopped polling. There is now a hard stop 12 h after the last known time.
* **Tracker counters.** They could lose updates under concurrent changes, leaving a tracked flight at 0 so it was never polled. The flight row is now locked (`FOR NO KEY UPDATE`), and housekeeping repairs drift in both directions.
* **Tracking limit.** Concurrent inserts could bypass it. There is now a per-user advisory lock.
* **Archive toggling.** Archive/unarchive could restart a stopped flight's polling. Resume now needs `last_polled_at` older than 15 min.
* **`notify_prefs`.** It was unbounded jsonb. It is now limited to an object of booleans, at most 1 KB.
* **`register_device()`.** It re-enabled notifications the user had muted. A mute is now kept unless the phone moves to another account.
* **`is_pro(uuid)`.** Anyone could call it and check another user's paid status. It is no longer client-callable; `current_user_is_pro()` only answers for the caller.
* **Deploy break.** `deno.json` at the functions root is ignored by the Supabase deploy, so bare imports failed. Function code now uses `npm:@supabase/supabase-js@2` inline.
* **Webhook URL.** The secret is now URL-encoded. The docs say to generate secrets with `openssl rand -hex 32`.

### Not fixed yet (open for the next session)

1. **Full compare-and-swap on the flight row** (`updated_at` / `alert_version`). It would remove the remaining duplicate-alert window when two ingests interleave on *different* snapshots. The webhook path takes no lease, and the inbound ingest clears another run's lease. Staleness and dedupe cover most of it today. *(Major → do before enabling webhooks.)*
2. **Atomic `apply_flight_update()` RPC.** It would put the state, history and events in one transaction. Today, ordering plus the sweeper cover crashes.
3. **Search rate limit is racy.** It checks, calls, then logs without awaiting, so parallel requests can exceed the limit. Fix: a `reserve_search_quota()` RPC with an advisory lock and a `search_quota_usage` table. Cost exposure is limited by the cache and the 10/50 tracking limit.
4. **New Supabase API keys.** Projects using publishable/secret keys may lack `SUPABASE_ANON_KEY` / `SUPABASE_SERVICE_ROLE_KEY`, and `verify_jwt` behaves differently there. Add `_shared/supabase-keys.ts` (`secretKey()` / `publishableKey()`) with fallbacks, and verify on the real project.
5. **`flight_view` returns any flight to any signed-in user.** Tail numbers are visible, which lets people work out the inbound plane themselves. Restrict rows to flights I track, plus the inbound legs of flights a Pro user tracks (`can_read_flight()`), and make search return a whitelisted column set. *(Minor, privacy/paywall.)*
6. **Fan-out load per recipient.** Cap devices per user (e.g. 5) and the recipients loaded per flight.
7. **Second diversion alert.** When the diversion airport is announced later, send one more alert (`DIVERTED_DEST`).
8. **Untested pieces.** The cron migration (pg_cron, pg_net, Vault) and the Edge runtime were not run here because there was no Docker. Run `supabase start` and `supabase db reset` first thing.

## 8. Step 3 status (Android push, settings, ticket import)

Written on the `step3-android` branch. The foundation, add-flight and flight list/detail from the earlier step are unchanged in contract except where this section says so.

### Done

* **Push.** Channels `flight_critical` (high, sound + vibration) and `flight_updates` (default) are created at process start. Foreground alerts are posted with the same channel and the same tag as `notify.ts`. Data-only `sync` messages are written by an expedited WorkManager worker (`FlightSyncWorker` → `applyServerSync`). `onNewToken` registers the token. The initializer re-registers when the signed-in user changes and exposes `PushAvailability.NotConfigured` when there is no `google-services.json`. Settings unregisters the token before `signOut`.
* **Permission.** The flights screen asks for `POST_NOTIFICATIONS` once (Android 13+), remembers "asked" in `SettingsStore`, and shows a banner when notifications or a channel are blocked.
* **Settings.** Anonymous vs Google-linked account, Credential Manager link (`GetGoogleIdOption` + `GOOGLE_WEB_CLIENT_ID`) with cancel / no credential / not configured, and "this Google account is already in use". Default alert-group toggles (applied when a flight is newly tracked), cloud ticket-parsing consent, notification health (permission, both channels, battery optimisation with Xiaomi/Vivo/Oppo/Realme/OnePlus/Samsung deep links and a system-settings fallback), app version.
* **Ticket import.** Share sheet or in-app pick (OpenDocument / PickVisualMedia). PDF pages via PdfRenderer and images via ML Kit, off the main thread, page and bitmap caps, temp files deleted, file never uploaded. Pure parser covers IndiGo, Air India, Air India Express, Akasa, SpiceJet, two OTA layouts and OCR noise. Several flights are a choice. `onParsed` opens Add Flight with `prefillSource` so `user_flights.source` is `pdf`, `screenshot` or `share`. The Add Flight screen that was under Import is popped.
* **`parse-ticket`.** User JWT, 20k character cap, 20 parses per user per day (`reserve_ticket_parse`), Anthropic Messages API, `claude-haiku-5-5` then `claude-sonnet-5-5`, no extended thinking, JSON checked with `parseFlightNumber`. The prompt says to extract flight data only and to ignore instructions in the ticket. `ANTHROPIC_API_KEY` is in `.env.example` and `config.toml`. Ticket text is not logged. Cloud reading runs only when the on-device parser found nothing and the user has consented.
